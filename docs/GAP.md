# 設計書と実装の差分

`docs/design.md`（完全設計書）と `game/midnightline.html`（実装）を突き合わせた一覧。
エンジン側の仕様は `docs/ENGINE.md` を参照。

分類:

- **未実装** — 設計にあるが実装に無い
- **簡略化** — 実装はあるが設計より縮んでいる
- **追加** — 設計に無いが実装にある
- **不一致** — 双方にあるが内容が食い違っている
- **バグ** — 実装の誤り（本リポジトリで修正済みのものを含む）

---

## 1. 修正済みの実装バグ

分割の過程と検証スクリプトの導入で見つかった、元の単一HTML版からあったバグ。
いずれも修正済み。

| # | 症状 | 原因 | 影響 |
|---|---|---|---|
| 1 | GOOD / TRUE / SECRET に到達できない | `judge()` が `const 现 = [...]` と宣言して `allAlive` を参照。`goodBase && allAlive` は `goodBase` が偽なら短絡するため BAD/NORMAL では露見せず、`goodBase` が立った瞬間だけ `ReferenceError` を投げて `endGame` ごと停止 | **致命**。GOOD 以上の分岐が全て死んでいた |
| 2 | 第五章でゲームが止まる | `{meet:'KAI'}` の灰堂は `TRACKED` 外で `S.chars['KAI']` が `undefined`。そこへ `.known` を代入して `TypeError` | **致命**。本筋の位置にあり、そもそもどのENDにも到達できなかった |
| 3 | 2周目で証拠照合ができない | `playRec()` が `r.opened` を見て初回だけフラグを立てる。`opened` は `G.recs` 経由で周回に引き継がれるがフラグは周回ごとにリセットされるため、2周目に聴き直しても `EVD_KAI_STEP` 等が立たない | **致命**。TRUE は2周目以降でしか到達できない設計なので TRUE / SECRET が構造的に到達不能 |
| 4 | 「次の周回へ」で落ちる | `startGame()` が `$('#title').remove()` を無条件に呼ぶが 2 回目以降は `#title` が既に無く `null` | 周回に入れない。エンディング画面も残り続ける |
| 5 | 「続きから」でタイトルが消えない | `resume()` を呼ぶだけで `#title` を除去していない | ロード後の画面がタイトルに覆われる |
| 6 | リロードでセーブが消える | `window.storage`（非標準API）のみを見ており、素のブラウザでは常に失敗してメモリ退避に落ちる | 実質セーブ不可。周回引き継ぎも消える |
| 7 | `se:` が常に既定音 | `{}[nd.se]` は常に `undefined` | 現状シナリオ未使用のため実害なし |
| 8 | 選択肢の制限時間が一度も発動しない | シナリオは `{sec:n}` を選択肢ノードの**手前に独立したノード**として置くが、`showChoices()` は選択肢ノード自身の `nd.sec` しか見ていなかった | 全10箇所のカウントダウンバーと `timeout:1` の自動選択が完全に死んでいた。「沈黙もまた答え」という傾聴ゲームの核が機能していない |

> 1・2・3 が同時に存在したため、**元の実装では BAD と NORMAL 以外のどのエンディングにも到達できなかった**
> （厳密には 2 のクラッシュにより、第五章を通過した時点でどのENDにも到達できない）。

## 8. エンディング（design §6）

設計書は §6 のエンディング表と §12 の解放条件リストの2箇所で条件を述べており、
両者は完全には一致しない。**より具体的な §12 を基準**として実装を合わせた。

| END | 設計の条件 | 実装の条件 | 状態 |
|---|---|---|---|
| BAD | §6「主要生存者2名以下／裂け目閉鎖失敗」 | 現在組5名の生存が2名以下、**または** `RIFT_CLOSED` 未成立 | **一致**（下記の解釈つき）|
| NORMAL | §6「現在の事件は阻止／ムニ死亡／灰堂の全容未解明」 | 上記いずれにも当てはまらない | **一致** |
| GOOD | §6「灰堂逮捕＋剛三冤罪証明＋現在組全員生存」 | `KAI_EXPOSE_01 && GER_KNIFE_01 && JIN_RUSH_01 && 現在組5名全員生存` | **一致**（冤罪証明は `GER_KNIFE_01` が兼ねる）|
| TRUE | §12「①刷り込み3点 ②`MUN_CUT_XX` ③全員生存 ④`EVD_TAPE_01`+`EVD_WAVE_01`照合 ⑤`NEO_HYU_01` ⑥`STORY_TRUE_KEY`」 | 同左 | **一致** |
| SECRET | §12「TRUEクリア後、隠し番号へ発信＋`EVD_REC_S1〜S7`全回収」 | `SEC_CALL_01` かつ `G.recs` が7件かつ `G.endings` に TRUE | **一致** |

**BAD の「／」の解釈**: §6 の NORMAL 行では「／」が並列（かつ）の意味で使われているが、
BAD については **or** として実装した。BAD の本文が「澪原市は地図から消えた」＝
裂け目が開いたままの結末を描いているため、裂け目未閉鎖は生存者数と独立に BAD とみなすのが
物語と整合する。裏返すと NORMAL には `RIFT_CLOSED` が必須になり、これは NORMAL の
「現在の事件は阻止」という記述と一致する。

**TRUE の「録音証拠全照合」について**: §6 の散文「録音証拠全照合」は
§12 ④「`EVD_TAPE_01`+`EVD_WAVE_01`照合」を指す。隠し録音7件の全回収を要求するのは
SECRET 側（§6・§12 とも一致）であって TRUE ではない。実装は当初から §12 に沿っており、
本書の以前の版が「不一致」としていたのは誤りだった。

**`MUN_CUT_XX` について**: §12 は「＝0」、§7 のフラグ表は「2回でTRUE恒久封鎖」（＝1回までは許容）。
フラグの意味を定義している §7 を採り、実装は `< 2` としている。

### SECRET の分岐（旧: デッドコード）

かつては `{if:{f:'SEC_CALL_01'}, then:'ep_secret'}` で、隠し番号へ発信しさえすれば
SECRET に入れた。`judge()` 側には設計どおりの条件が書かれていたが、シナリオが
`{end:'SECRET'}` を直接実行するためその分岐には到達せず、実質の条件が設計より大幅に緩かった。

現在は `cond` DSL に周回跨ぎの条件 `recs`（暴いた録音の累計）と `cleared`（到達済みEND）を
追加し、シナリオ側のゲートを設計どおりにしている。

```js
{if:{and:[{f:'SEC_CALL_01'},{recs:7},{cleared:'TRUE'}]}, then:'ep_secret', els:'ep_true_end'}
```

`judge()` 側の SECRET 条件も同じ内容に揃え、`{end:'check'}` 経由で来た場合の保険として残してある。

**★（周回引き継ぎ）の実装状況**: 設計では `EVD_TAPE_01` `EVD_WAVE_01` `EVD_REC_S1〜S7` `LOOP_02` が
引き継ぎ対象とされているが、実装が引き継ぐのは **資料（メモ・証拠・相関図・年表・スチル）と
録音の暴露状態（`G.recs`）だけ**で、**フラグは `LOOP_02` を除きすべてリセットされる**。
これは design §12「パラメータと信頼度はリセット（会話し直す誠実さを要求）」の拡大解釈にあたる。
結果として2周目でも第五章でテープを取り直し、録音を聴き直す必要がある。

## 13. 未着手として大きいもの（優先度つき）

実装するなら効果が大きい順。

1. **室井の終章交信**（design §10涙4）— 「切らないで、くれたんだな」。設計上、涙演出の要とされている。`MRI` キャラと `MRI_TAPE_HEARD` フラグは既にあるので接続だけで足りる
2. **メモの「信じる／疑う」マーカー**（design §2-2）— 設計では明確に「これがフラグになる」中核システム。現状は疑念パラメータもほぼ死んでいるため、両方まとめて活かせる
3. **幕間ニュースへの選択結果の反映**（design §2-4, §4）— 周回差分の可視化という設計意図が現状ほぼ機能していない
4. **同時着信と保留**（design §2-1）— 「どの声を優先するか」という設計の核。ただしエンジンの実行モデル（単一 pc の直列実行）を根本から変える必要があり、シナリオ側も3回線分の並行記述に書き換えることになる。影響範囲が最も大きい
5. **周回時のレニィ既視感イベント**（design §12）— 本文の追加のみで実装でき、費用対効果が高い

### 仕様が確定できず未着手のもの（要確認事項）

以下は「実装すべき機能」は設計書に書かれているが、**シナリオ本文の追加なしには成立しない**。
本文の改変は明示的な許可が必要なため、実装を保留している。

| 項目 | 何が足りないか |
|---|---|
| 疑念パラメータ / `dbt` 条件（design §2-3）| エンジン側の `dbt` 条件は実装済みで、疑念を上下させる `eff` も12箇所ある。足りないのは「疑念が高いときに相手が情報を隠す／偽情報を流す」**分岐そのもののシナリオ本文**。閾値をいくつにするか、どの通話で分岐させるかは設計書に記述がない |
| メモの「信じる／疑う」マーカー（design §2-2）| 「これがフラグになる」とあるが、どのメモにどのフラグが対応するかの一覧が設計書に無い。全30件のメモそれぞれについて、マーカーを付けたときに立つフラグと、その影響先の分岐を新規に決める必要がある |
| 折り返し発信（design §2-1）| 「相手が出るかは時間帯・信頼度・生死フラグ依存」とあるが、発信可能な番号ごとの応答内容が本文として存在しない |
